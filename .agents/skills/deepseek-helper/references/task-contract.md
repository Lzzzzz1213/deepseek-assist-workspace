# 任务拆分与任务契约

主智能体用本页把需求转成可直接执行、可逐条审查的任务。这里是提示词模板，不代替 `-EditableFiles`、哈希校验或脚本的独占锁；不要求用户为日常拆分逐次确认。

## 如何拆分

- 一个任务对应一个可验收行为。通常 1–2 个文件；同一组件的结构、样式和说明可合成一个闭环。不要把无关修复装进一次委派，也不按行数机械拆碎。
- 委派前先定位入口、调用方/消费者和项目内参考用法，并在 TaskFile 写清逐文件工具页数/字符预算、精确修改片段和反例；未经核对的猜测代码不写入方案。接口未知时先只读调查，契约稳定后再单列实施任务，不边猜协议边写。
- 先看实际文件、调用方与已有差异，再划写入清单。说明哪些文件已经有改动、必须保留什么。依赖尚未稳定的上下游按顺序做；只有文件清单和行为边界均独立的任务才并行。
- 主智能体决定跨层接口与关键语义：签名、字段类型/格式、路径、返回状态、持久标识和失败处理。给出正常、边界或失败示例；不要只写“保持兼容”“处理所有异常”。
- 普通样式和小函数交给辅助实际实施。身份/安全边界、删除/卸载等复杂任务先由主智能体确定不变量、失败路径和方案，再委派局部实现；不能隔离就由主智能体完成。不要用增加提示词篇幅代替消除设计歧义。
- 长文件的小修改优先 `replace_text`；不能把整个大功能塞进一轮。逐文件写明保留 LF/CRLF 与 UTF-8 BOM 的要求，并给字符串、正则、路径的输入输出例；不要把 JSON、PowerShell、正则的转义混为一谈。
- 根据每文件首读、一次写入和完整回读估算最低工具调用数；预算吃紧先缩小目标或补齐上下文，不能靠重复超限请求继续。估算不保证成功，也不把上限一律调到 100。

## 可复制的 TaskFile

```text
目标：<一个行为；写明触发条件与预期结果>
项目目录：<绝对目录，实际权限以入口的 WorkingDirectory 为准>
允许修改且由你独占：<逐项具体相对路径，须与 EditableFiles 相符；只读任务填无>
已有改动：<相关未提交改动及必须保留的部分>
禁止扩展：<本次无关模块、配置、依赖和授权边界；不能提交/推送/发布或递归委派>

先读：<最少必要入口、调用方/消费者、项目规范；不要求扫描整个项目>
参考定位：<入口、调用方/消费者、项目内已有用法；没有则写“未找到”>
工具与文本：<逐文件首读页数/字符、write_file 或 replace_text 的最低调用数；行尾与 BOM；old_text/new_text 或最终片段及转义层次>
接口与不变量：
- <真实签名/字段类型与精确格式；谁生成、谁消费>
- <必须保持的行为和关键失败路径>
正例：<具体输入 -> 输出/行为；文字替换给出 old_text 出现次数、new_text 和预期行尾>
反例或边界：<具体输入 -> 拒绝/回退/保留行为；包含看似可替换但应零次或多次命中的片段>
实施范围：<已确认的方案要点；不要提供未经核对的猜测代码>

验收：
1. <可在实际代码与回读中判定的结果>
2. <与接口和不变量对应的边界，不重复空泛要求>
验证归属：你完整读取后在清单内实际修改并回读；主智能体收回文件后统一审查完整差异、编译/类型检查。测试和运行按用户及项目授权执行；未执行的检查必须说明。
阻塞：缺少关键接口、需扩大范围、哈希冲突或工具预算不足时，报告已做与剩余项，不扩权限、不盲目重试。
返回：完成/部分完成/阻塞；逐项验收状态与文件行号；实际检查及未执行的验证；改动文件；风险。不要将待主审写为最终通过。
```

## 受限 MCP 与文本语义

- `read_file` 默认最多 1000 行，仍受 32000 字符预算；回包返回 `line_ending`、`utf8_bom`、`next_start_line`，以及原有 SHA256/`full_file_read`。任务按实际页数要求读到 `full_file_read=true`，不把续页误判为完整读取。
- `write_file` 用于新文件或必要的整份重写。`replace_text(path, old_text, new_text, expected_sha256)` 只在 `-EditableFiles` 清单内的既有文件中替换唯一字面片段：`old_text` 非空且必须恰好出现一次，真实换行按目标文件统一的 LF/CRLF 规范匹配。先完整读取原文件，再提交返回的最新 `expected_sha256`；写后必须完整回读。不得建议 shell、patch 或原生编辑绕过。
- 每次工具回包附 `budget.used`/`budget.remaining`/`budget.delivery_reserve`，`write_file`/`replace_text` 回包同样附预算。入口在调用模型前按待改文件首读、一次写入、完整回读估算最低工具调用数；达不到就拒绝开始，由主线程缩小任务或补齐上下文。
- 临近工具预算且仍需交付时，MCP 以 `delivery_budget_reserved` 拒绝额外 list/search/非目标文件读取。模型应立即停止探索，优先完成目标的读写回读；必要接口仍未知就交还主线程，不猜测。失败调用也计数；被拒请求不得原样重试。
- 工具层保持目标文件原有 UTF-8 BOM 与 LF/CRLF 规范，不提供运行命令能力。疑似整份多行文件被写成字面 `\n` 单行时，写入应拒绝，不自动二次反转义；模型应改正输入，而不是要求工具解码。

### 转义与示例

- JSON 源码中的 `"\\d+"` 解析后是正则 `\d+`；任务里的“语义输入”应写解析后的值，不能把 `\\n` 再自动解码成换行。需要真实换行时，`old_text` 直接包含换行。
- PowerShell 单引号字面量不使用 C 风格反斜杠转义：`'C:\tmp\a.txt'` 的反斜杠就是路径字符，不应改成 `'C:\\tmp\\a.txt'`，除非目标路径本身需要两个反斜杠。
- 正则按目标语言的语法单独给出，如 `^[0-9a-f]{32}$`；路径、普通字符串和正则的示例分别标注，不能互相套用转义规则。

例如已有接口要求群 ID 为 32 位小写十六进制，任务应明确给出 `^[0-9a-f]{32}$`、稳定性要求和消费者约束，并注明 `workspace|<hash>` 不合法。给例子是为了消除歧义，不要求所有项目都采用这种 ID。

## 主审与续做

确认进程结束并收回文件、锁后，审查范围、完整差异、接口不变量和实际验收结果，核对实际字节、行尾、UTF-8 BOM 与修改字符串的语义，而不是只看显示文本。必要语法/编译检查及针对具体样例的验证由主线程执行。`success=true` 只计调用完成，不证明落盘、完整回读或一次做对；记录 `passed` 前写清实际检查和主智能体补救。发现问题时提供具体失败输入、当前错误行为、预期行为和新的最小文件清单；先核对部分改动，不把原任务原样反复重跑。主审仍由主智能体完成，不能让辅助自评取代验收。
